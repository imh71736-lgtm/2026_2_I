SECTION 01
단방향 암호화(해시 함수)란?

단방향 암호화(해시 함수)는 어떤 데이터든 받아 고정 길이의 문자열로 변환합니다. 핵심은 되돌릴 수 없다는 점입니다. 결과값(해시)으로 원본을 복원하는 것은 원칙적으로 불가능합니다. (단, 모든 경우를 시도하는 무차별 대입 공격은 이론적으로 가능하지만 현실적으로 불가능)

🧪 코로나 백신 증명서 QR 인증 시뮬레이터
⚠️ 왜 전자서명은 반드시 해시를 거치는가? RSA 등 비대칭 알고리즘은 키 길이보다 큰 데이터를 직접 처리할 수 없고, 원문에 직접 서명하면 성능이 매우 느리며 보안 취약점도 발생합니다. 이 때문에 RSA-PSS, ECDSA 등 현재 사용되는 모든 전자서명 표준은 해시를 필수 단계로 포함하고 있습니다.

코로나 백신 증명서 QR 인증 과정을 직접 체험합니다. 정부 역할로 QR을 발급하고, 검사원 역할로 검증하고, 위조범 역할로 탐지를 경험해보세요. 실제 SHA-256과 HMAC이 동작합니다.

📡 코로나 백신 증명서 QR 발급 과정

본인 인증
앱 설치 후 휴대폰 번호 + 주민번호 뒷자리로 본인 확인. 접종 이력이 있는 사람에게만 QR이 발급됩니다.
서버에 QR 발급 요청
앱이 HTTPS로 티켓 서버에 요청합니다.
[사용자 앱] → HTTPS → [질병관리청 서버] "백신 증명 QR 발급해줘"
서버에서 QR 생성
서버가 DB에서 접종 이력을 꺼내 아래 과정을 수행합니다.
① 이름 + 생년월일 + 접종여부 + 발급 시각 묶기 → ② SHA-256 해시 → ③ 질병관리청 개인키로 전자서명 → ④ QR 이미지 생성
QR을 앱으로 전송 → 화면 표시
HTTPS로 QR 이미지를 내려보냅니다. QR은 15~30초 후 자동 갱신되어 캡처 재사용이 불가능합니다.

🔍 QR 스캔 후 인증 과정

QR 데이터 추출 — 원본 데이터는 평문으로 저장
QR 안에는 두 가지가 들어있습니다.
① 원본 데이터 (평문) 이름·생년월일·접종여부·발급시각이 암호화 없이 그대로 저장됩니다. 스캔만 하면 누구나 읽을 수 있습니다.

② 전자서명 SHA-256(원본 데이터)을 질병관리청 개인키로 암호화한 값. 위조 여부를 검증하는 용도입니다.

⚠️ 원본 데이터가 평문으로 들어있어 검사원 앱에서 이름·접종여부를 바로 표시할 수 있습니다. 반면 개인정보 노출 문제로 코로나 패스가 비판받기도 했습니다.
이름·접종여부 화면 표시
① 원본 데이터(평문)를 그대로 읽어 검사원 앱 화면에 표시합니다.
→ 홍길동 / 백신 접종 완료 / 2022-03-01 발급
검사원이 눈으로 직접 확인하는 단계입니다.
공개키로 서명 되돌림 → 해시A 추출
검사원 앱에 미리 설치된 질병관리청 공개키로 전자서명을 복호화합니다. 인터넷 없이도 오프라인 검증이 가능합니다.
해시A = 공개키로 되돌린 값 (서명에서 추출)
원본 데이터 직접 해시 → 해시B 계산
QR의 원본 데이터(평문)를 앱이 직접 SHA-256으로 계산합니다.
해시B = SHA-256(원본 데이터)
해시A == 해시B 비교 → 위조 검증
일치 → ✅ 데이터 위조 없음  |  불일치 → ❌ 위조 탐지

🔁 대칭 암호화 & OTP 원리

대칭 암호화란?

대칭 암호화는 암호화할 때와 복호화할 때 같은 키를 사용하는 방식입니다. 서버와 사용자가 동일한 비밀키를 공유하고, 그 키로 데이터를 잠그고 엽니다.

⚡

대칭 암호화

같은 키로 잠그고 엶.
빠르지만 키 사전 공유 필요.
AES, DES 등

🔑🗝️

비대칭 암호화

다른 키로 잠그고 엶.
느리지만 공개키만으로 배포 가능.
RSA, ECC 등

💡 HTTPS는 두 방식을 함께 씁니다 — 비대칭으로 키를 교환하고, 이후 실제 데이터는 대칭(AES)으로 빠르게 암호화합니다.

📱 OTP — 대칭키의 대표 응용

OTP(One-Time Password)는 서버와 내 기기가 같은 비밀키(시드값)를 공유하고, 같은 시간 기준으로 동일한 OTP 값을 계산하는 대칭키 방식입니다.

STEP 01 시드값(비밀키) 공유
최초 앱 등록 시 QR 스캔으로 시드값을 기기에 저장합니다. 이후 네트워크로 전송되지 않습니다.
서버 시드값 == 내 앱 시드값 (대칭키)
STEP 02 HMAC-SHA1로 OTP 계산
서버와 앱이 동시에 같은 계산을 합니다.
HMAC(시드값, 현재시각 ÷ 30) → 해시값 → 6자리 추출
STEP 03 숫자 비교 → 인증
서버가 계산한 값 == 사용자가 입력한 값이면 인증 성공. 6자리가 일치한다는 것은 같은 시드값을 가졌다는 증명입니다.

⏱️ 30초 지나면 어떻게 될까?

서버는 정확히 현재 구간만 허용하지 않고 앞뒤 1구간씩 총 90초 범위를 허용합니다. 폰과 서버의 시계가 완벽히 일치하지 않거나 타이핑 시간이 걸리기 때문입니다.

⚠️ 비대칭 암호화가 느린 이유: RSA의 암호화(me mod n)·복호화(cd mod n) 연산에서 e, d, n이 실제로 2048비트 이상의 매우 큰 수이기 때문입니다. 이 큰 수의 모듈러 거듭제곱 연산 자체가 연산량이 많아 느립니다. 반면 대칭 암호화(AES)는 비트 치환·교환의 단순 반복 연산이라 하드웨어 가속도 잘 되어 훨씬 빠릅니다.
⚠️ 시드값 보안: 시드값이 탈취되면 공격자는 동일한 OTP를 생성할 수 있으므로 매우 위험합니다. 시드값은 최초 등록 시에만 전달되며 이후 네트워크로 전송되지 않습니다.

비대칭 암호화란?

비대칭 암호화는 암호화와 복호화에 서로 다른 두 개의 키를 사용하는 방식입니다. 공개적으로 배포하는 공개키(Public Key)로 암호화하고, 본인만 갖고 있는 개인키(Private Key)로 복호화합니다. 공개키로 암호화한 데이터는 대응되는 개인키로만 복호화할 수 있습니다.

🔓
PUBLIC KEY

공개키

누구에게나 공개.
이 키로 암호화 또는
서명 검증에 사용됨.

⇄
🔐
PRIVATE KEY

개인키

절대 공개하지 않음.
이 키로 복호화 또는
서명 생성에 사용됨.

💡 비유: 공개키는 누구나 넣을 수 있는 우편함 투입구, 개인키는 그 우편함을 여는 열쇠입니다. 투입구로 넣은 편지는 열쇠 없이 꺼낼 수 없습니다.

📡 두 가지 사용 방식

🔒

암호화 / 복호화

공개키로 암호화
→ 개인키로 복호화
수신자의 공개키로 잠가서 수신자만 열 수 있게

✍️

전자서명 / 검증

개인키로 서명
→ 공개키로 검증
발신자가 서명, 누구나 공개키로 진위 확인

SECTION 06-1
🔢 RSA 수학 원리 & 시뮬레이터

🔢 RSA 키 생성 수학 원리

두 소수 p, q 선택
서로 다른 큰 소수 두 개를 고릅니다.
예) p = 5, q = 11
실제 RSA에서는 2048비트 이상의 큰 소수를 사용합니다. 큰 소수는 단순 나눗셈 대신 밀러-라빈(Miller-Rabin) 확률적 판별법으로 빠르게 생성합니다. 40라운드 반복 시 오판 확률 ≈ 4-40 (사실상 0).
n = p × q 계산 (공개값)
두 수의 곱 n은 공개키와 개인키 모두에 포함됩니다.
n = 5 × 11 = 55
φ(n) = (p−1)(q−1) 계산 (오일러 피 함수)
n보다 작으면서 n과 서로소인 양의 정수의 개수입니다.
φ(55) = (5-1)(11-1) = 4 × 10 = 40
공개키 e 선택
1 < e < φ(n) 이고, gcd(e, φ(n)) = 1 을 만족하는 e를 선택합니다.
e = 7 (gcd(7, 40) = 1 ✅)
개인키 d 계산
e × d ≡ 1 (mod φ(n)) 을 만족하는 d를 구합니다 (모듈러 역원).
7 × 23 = 161 = 4×40 + 1 → d = 23
키 쌍 완성
공개키: (e, n) = (7, 55) — 공개 배포
개인키: (d, n) = (23, 55) — 비밀 보관
p, q, φ(n)은 키 생성 후 폐기합니다.
암호화 (공개키)
c = me mod n
평문 m → 암호문 c
복호화 (개인키)
m = cd mod n
암호문 c → 평문 m
🔒 보안의 핵심: n을 소인수분해해서 p와 q를 알아내지 못하는 한 개인키 d를 구할 수 없습니다. 실제 RSA는 2048비트 이상의 거대한 수를 사용해 현실적으로 해독이 불가능합니다.

🌐 HTTPS 비대칭 암호화 과정

HTTPS는 비대칭 암호화(느리지만 안전)와 대칭 암호화(빠름)를 조합합니다. 비대칭으로 세션키를 안전하게 교환한 뒤, 실제 데이터는 빠른 대칭(AES)으로 암호화합니다.

서버가 공개키 전달
브라우저가 접속하면 서버가 자신의 공개키(인증서 형태)를 전송합니다.
[서버] → 공개키(인증서) → [브라우저]
브라우저가 세션키 생성
브라우저가 이번 연결에서만 쓸 임시 대칭키(세션키)를 랜덤 생성합니다.
세션키 = random AES key (128~256비트)
세션키를 서버 공개키로 암호화해서 전송
브라우저가 세션키를 서버의 공개키로 암호화해 전송합니다. 공개키로 잠갔으니 서버 개인키로만 열 수 있습니다.
[브라우저] → 암호화된 세션키 → [서버]
서버가 개인키로 세션키 복호화
서버만 가진 개인키로 복호화해 세션키를 꺼냅니다. 이제 양쪽 모두 같은 세션키를 보유합니다.
서버 개인키(세션키 암호문) → 세션키 복원
이후 통신은 세션키(대칭 AES)로 암호화
느린 비대칭은 세션키 교환 1회만 사용하고, 이후 모든 데이터는 빠른 AES 대칭 암호화로 주고받습니다.
[브라우저] ⇄ AES(세션키) ⇄ [서버]
💡 핵심: 비대칭은 "느리지만 사전 공유 없이 안전하게 키 전달"이 가능합니다. 대칭은 "빠르지만 키를 미리 공유해야" 합니다. HTTPS는 비대칭으로 대칭키를 교환해 두 장점을 모두 취합니다.

SECTION 06-5
✍️ 전자서명
서명이란? 암호화된 것을 푸는 복호화와 달리, 서명은 해시값에 개인키를 적용해 "나만 만들 수 있는 값"을 새로 생성하는 행위입니다. 수식은 복호화와 동일(cd mod n)하지만, 입력이 암호문이 아닌 해시값이고 목적이 기밀성이 아닌 인증·무결성 증명이라는 점에서 구분됩니다.

✍️ 전자서명 과정

🖊️

서명 생성 (송신자)

서명 대상 데이터 → SHA-256 → 해시값
→ 개인키로 서명
개인키 보유자(송신자)가 수행

🔍

서명 검증 (수신자)

서명 → 공개키로 되돌림 → 해시A
수신한 데이터 → SHA-256 → 해시B
해시A == 해시B? → ✅ 유효

⚠️ 왜 반드시 해시를 거치는가? RSA 등 비대칭 알고리즘은 키 길이보다 큰 데이터를 직접 처리할 수 없고, 원문에 직접 서명하면 성능이 매우 느리며 보안 취약점도 발생합니다. RSA-PSS, ECDSA 등 모든 전자서명 표준은 해시를 필수 단계로 포함합니다.

📋 전자서명 단계별 흐름

단계과정수행 주체
서명 생성 서명 대상 데이터(예: 거래 내용, 로그인 요청) → SHA-256 → 해시값 → 개인키로 서명 개인키 보유자(송신자)
서명 검증 서명 → 공개키로 되돌림 → 해시A, 수신한 서명 대상 데이터 → SHA-256 → 해시B, 해시A == 해시B? 공개키 보유자(수신자)

🏦 공동인증서 전자서명 흐름

사용자가 거래 내용에 개인키로 서명
은행 앱이 "100만원 이체" 같은 거래 데이터를 SHA-256으로 해시한 뒤, 사용자 기기에 저장된 개인키로 서명값을 생성합니다.
서명값 + 인증서(공개키) 전송
서명값과 함께 사용자의 인증서(공개키 포함)를 은행 서버로 전송합니다. 공개키는 이 단계에서 은행에 전달됩니다.
은행이 CA에 인증서 유효성 확인
은행 서버가 CA(인증기관)에 조회해 "이 인증서가 실제로 CA가 발급한 것인지" 확인합니다.
공개키로 서명 검증
인증서의 공개키로 서명값을 되돌려 해시A를 추출하고, ②단계에서 서명값과 함께 전송된 거래 데이터 원문을 직접 SHA-256해서 해시B를 만들어 비교합니다.
해시A == 해시B → ✅ 본인이 서명한 거래 확인
